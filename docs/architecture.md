# Как устроен сервер

Здесь описано, как связаны MCP-сервер, скиллы и инструменты и как языковая модель управляет их вызовом. Установка и подключение описаны в [README](../README.md).

## Схема

```
Claude Desktop ────── stdio ─────┐
claude.ai ───── HTTP + туннель ──┤
консольный клиент ─── stdio ─────┼─► server.py ─► реестр скиллов ─┬ DataLoadingSkill        list_data_files, load_data, describe_data
Telegram-бот (через клиент) ─────┘   (MCPServer)                  ├ DataCleaningSkill       clean_data
                                          │                       ├ VisualizationSkill      suggest_charts, plot_trend,
                                          │                       │                         plot_distribution, correlation_analysis
                                          │                       ├ AbcAnalysisSkill        abc_analysis
                                          │                       └ InsightGenerationSkill  collect_findings, save_report
                                          │
                        workflow.py: порядок шагов      store.py: dataset_id → таблица
```

| Файл | За что отвечает |
|---|---|
| `server.py` | Точка входа: разбирает аргументы и запускает сервер по stdio или по HTTP |
| `analytics_mcp/app.py` | Собирает сервер из скиллов, найденных реестром |
| `analytics_mcp/registry.py` | Реестр: базовый класс скилла, декораторы `@register_skill` и `@tool`, поиск файлов в папке `skills/` |
| `analytics_mcp/workflow.py` | Собирает порядок шагов из скиллов: инструкцию сервера, промпт и подсказку `next_step` |
| `analytics_mcp/store.py` | Хранит таблицы и состояние анализа по `dataset_id` |
| `analytics_mcp/columns.py` | Определяет типы колонок: дата, число, категория, код, текст |
| `analytics_mcp/skills/` | Пять скиллов, по одному файлу на скилл |
| `analytics_mcp/charts.py`, `style.py` | Общий путь от графика matplotlib к ответу инструмента, палитра и подписи |
| `analytics_mcp/report.py` | Правила для выводов модели, содержание отчёта и его текст в Markdown |
| `analytics_mcp/report_pdf.py` | Рисует PDF по тому же содержанию, по которому написан Markdown |
| `clients/` | Консольный клиент на OpenRouter и Telegram-бот |

## Что здесь называется скиллом

В задании скилл это серверный класс, который отвечает за один этап анализа. Так он и сделан: скилл это класс, инструменты это его методы с декоратором `@tool`. Модель видит инструменты. Скиллы она видит только в тексте инструкции, где этапы перечислены по порядку.

У слова есть ещё два значения, их здесь нет. Навык Claude это папка с файлом `SKILL.md`, которую загружает клиент. В SDK `mcp` есть расширение, где сервер отдаёт такие файлы как ресурсы. Я его не использовал: задание описывает скиллы как серверную логику.

## Как модель узнаёт порядок шагов

Порядок хранится в сервере и собирается из скиллов. У каждого скилла три вещи:

- `stage`: номер этапа, по нему скиллы сортируются;
- `is_done(analysis)`: выполнен ли этап для этой таблицы;
- `hint(analysis)`: какой инструмент вызвать, чтобы этап выполнить.

`Workflow` проходит по скиллам и находит первый невыполненный этап. Его подсказка и есть следующий шаг. К модели порядок попадает четырьмя путями:

| Путь | Когда модель его видит |
|---|---|
| Поле `instructions` сервера | При подключении, если клиент его передаёт |
| Промпт «Проанализировать файл» | Когда пользователь сам выбирает его в клиенте |
| Поле `plan` в ответе `load_data` | После первого вызова |
| Поле `next_step` в ответе каждого инструмента | После каждого вызова |

Путей несколько, потому что `instructions` выполняют не все клиенты. На пробном сервере с одним инструментом обычный чат Claude Desktop и ChatGPT указание из `instructions` не выполнили, вкладка Code и claude.ai выполнили. Подсказка в ответе инструмента доходит до любой модели, которая сделала хотя бы один вызов.

Порядок подсказывается, жёстко сервер требует двух вещей. Первая: после очистки график и итоги считаются только по очищенной таблице. На вызов со старым `dataset_id` приходит ошибка с правильным, иначе график с дубликатами и выбросами разошёлся бы с выводами отчёта. Вторая: `save_report` не собирает отчёт, пока не пройдены статистика, очистка, нужное число графиков и `collect_findings`. Ошибка перечисляет незавершённые этапы и называет следующий вызов. На прогоне модель, которой велели сохранить отчёт сразу после загрузки, получила такой отказ, прошла этапы и собрала отчёт со второй попытки. В остальном модель свободна: может вызвать `abc_analysis` раньше или построить графики до очистки.

Консольный клиент своего промпта не имеет. Системным промптом ему служит `instructions` сервера, слово в слово.

## Как передаётся таблица

DataFrame через MCP не передать: протокол возит JSON. Таблица остаётся в памяти сервера, а `load_data` возвращает короткий `dataset_id`. Остальные инструменты принимают его вместо аргумента `df` из задания.

`clean_data` исходную таблицу не меняет. Он сохраняет очищенную под новым `dataset_id` и возвращает его. Обе таблицы делят одно состояние анализа: журнал очистки, список графиков, цифры для выводов, путь к отчёту. По этому состоянию скиллы и отвечают, выполнен ли их этап.

Идентификатор передаётся явно в каждом вызове. Сервер работает по HTTP без сессий, поэтому «текущей таблицы» у него нет.

## Кто считает и кто пишет

| Шаг | Кто делает |
|---|---|
| Статистика, очистка, графики, цифры для выводов | Код сервера |
| Формулировки выводов и рекомендаций | Модель, по цифрам из `collect_findings` |
| Форма выводов и рекомендаций | Сервер: схема `save_report` и проверка в `report.py` |
| Сборка отчёта | `save_report`: главные числа, выводы, рекомендации, графики с подписями, журнал очистки |
| Короткий ответ для чата | Сервер, из тех же выводов (поле `chat_summary`) |

Каждый инструмент возвращает, что он реально сделал, с числами: сколько строк удалено, чем заполнены пропуски, сколько выбросов исключено. График возвращается двумя блоками: текст с фактами и картинка PNG. Факты нужны, потому что текстовая модель картинку не видит.

Модель присылает выводы и рекомендации объектами: вывод это фраза до восьми слов (`headline`) и пояснение с цифрой (`evidence`), рекомендация это действие (`action`) и причина (`reason`). Выводов от трёх до пяти, рекомендаций от двух до четырёх. Нарушения приходят одной ошибкой со списком, модель исправляет вызов. Так отчёт выглядит одинаково у разных моделей. Форму я проверил запусками консольного клиента на `deepseek/deepseek-v4.1-flash`, `openai/gpt-6.1-terra` и `qwen/qwen3.8-flash`: все три передали выводы в нужной форме с первого вызова. Журналы этих запусков в репозиторий не выложены.

Ошибка возвращается ошибкой и говорит, что исправить: называет подходящие колонки, существующие листы, файлы в папке. На прогонах модель получала такую ошибку и исправляла вызов сама.

## Как выбраны правила очистки и графиков

- Типы колонок определяются по значениям. Имя колонки учитывается в одном случае: оно отличает код (год, почтовый индекс, номер заказа) от показателя.
- Выбросы делятся на два уровня. Значение дальше 6 межквартильных размахов от квартиля исключается из расчётов, строка остаётся в таблице. Значение дальше 3 размахов остаётся в расчётах и передаётся человеку. Первое правило с одним порогом пометило настоящую декабрьскую продажу, это было видно на прогоне.
- Исключается только то, что похоже на ошибку ввода: таких значений не больше 2% строк, и между ними и остальными есть разрыв не меньше 3 размахов. Это условие появилось после прогона на Superstore. Там крупные заказы идут сплошным хвостом, и правило без него исключало 281 строку, треть суммы продаж. Длинный хвост сервер оставляет в расчётах и сообщает, сколько в нём строк и какая это доля суммы.
- Сезонность считается при данных за 24 месяца и больше. По одному году её не отличить от разового события.
- `suggest_charts` подбирает графики по типам колонок: дата и число дают динамику, категория и число дают столбцы, число даёт гистограмму, две числовые колонки и больше дают корреляции.

## Чем отличаются транспорты

Скиллы и инструменты в обоих режимах одни. Отличается запуск и то, что сервер считает безопасным.

| | stdio | Streamable HTTP |
|---|---|---|
| Запуск | `python server.py` | `python server.py --http` |
| Кто подключается | Claude Desktop, консольный клиент, бот | claude.ai |
| Какие файлы читает | Любой путь на машине. С флагом `--data-only` только папку `data/` | Только папку `data/` |
| Имя таблицы | `sales_data_1` | `sales_data_1_` и случайный хвост |
| Как пользователь получает отчёт | Файл на диске. С `ANALYTICS_OPEN_REPORT=1` сервер открывает PDF | Ссылка на PDF со случайным ключом |

По HTTP адрес сервера публичный, поэтому он читает одну папку: без ограничения любой, кто знает адрес, прочитал бы файлы на машине. Бот тоже публичный вход, и сервер под ним запускается с `--data-only`.

Два решения в HTTP-режиме вызваны туннелем. Быстрый туннель Cloudflare не пропускает SSE, поэтому сервер отвечает обычным JSON (`json_response=True`). SDK принимает запросы только со своим адресом в заголовке `Host`, поэтому адрес туннеля добавляется в разрешённые через `--public-host`.

## Как добавить скилл

1. Создать файл в `analytics_mcp/skills/`.
2. Объявить в нём класс-наследник `Skill` с декоратором `@register_skill`, задать `stage`, `title` и `guide`.
3. Пометить методы-инструменты декоратором `@tool`.

Сервер сам найдёт файл, зарегистрирует инструменты и впишет этап в инструкцию по номеру `stage`. Обязательный этап дополнительно реализует `is_done` и `hint`, тогда он участвует в подсказке `next_step`. Необязательному они не нужны.

Так добавлен ABC-анализ: коммит `7a21324`, в диффе один файл `analytics_mcp/skills/abc.py`. Тест `tests/test_extension.py` объявляет пробный скилл прямо в тесте и проверяет, что инструмент появился в списке и встал между графиками и выводами.

Граница расширяемости такая: состояние четырёх базовых этапов хранится полями общего класса `Analysis`. Новому скиллу для своих данных отведён словарь `extra` в том же классе.
