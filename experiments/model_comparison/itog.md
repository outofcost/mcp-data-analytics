# Что показало сравнение моделей

Прогоны провёл 11 ноября 2026. Условия и правило решения записал в `protocol.md` до первого прогона, хэш файла лежит в `protocol.sha256`. Таблицу посчитал `score.py`, она лежит в `results.md`. Сырые журналы лежат в `runs/`.

## Главное

1. По правилу протокола гипотеза не подтвердилась: порядок держится не на всех четырёх моделях.
2. На `deepseek/deepseek-v4.1-flash` и `openai/gpt-6.1-terra` цепочка выдержана в 12 прогонах из 12, на обоих файлах, без единой ошибки инструмента.
3. Слабая `mistralai/mistral-nemo` не выдержала цепочку ни разу: 0 из 6.
4. По `qwen/qwen3.7-flash` результата нет: провайдер оборвал все 12 попыток по протоколу и все 12 попыток повторной серии.
5. Вне протокола соседняя модель `qwen/qwen3.8-flash` выдержала цепочку в 6 прогонах из 6. Общий вывод по протоколу эта серия не меняет.

## Что получилось по моделям

| Модель | Цепочка выдержана | Закономерностей из 3 на `sales_data.csv` | Цена прогона | Время прогона |
|---|---|---|---|---|
| `deepseek/deepseek-v4.1-flash` | 6 из 6 | 3, 3, 3 | 0,003 $ | 24 с |
| `openai/gpt-6.1-terra` | 6 из 6 | 3, 3, 3 | 0,015 $ | 37 с |
| `mistralai/mistral-nemo` | 0 из 6 | 0, 0, 0 | 0,0001 $ | 3 с |

Цифры первых четырёх строк взяты из `results.md`, последней из `results_qwen38_addition.md`.

## Почему слабая модель не прошла

`mistralai/mistral-nemo` в четырёх прогонах из шести не вызвала ни одного инструмента, в двух вызвала только `list_data_files`. Она отвечала фразой вроде «Сначала загружу данные» и на этом останавливалась (`runs/mistral-nemo__*/answer.md`). Клиент заканчивает работу, когда модель отвечает текстом без вызова.

Подсказка `next_step` приходит в ответе инструмента. Если модель не сделала первый вызов, подсказке негде появиться. Вывод: серверный порядок работает для модели, которая умеет вызывать инструменты. Нижний порог по модели есть.

Колонка «Этапы по порядку» у этой модели показывает 6 из 6: при нуле вызовов порядок нарушить нечем. Смотреть нужно на колонку «Цепочка выдержана».

## Почему нет результата по Qwen

Провайдер Alibaba вернул через OpenRouter ошибку 429 «temporarily rate-limited upstream» во всех шести прогонах и во всех шести повторах. Текст ошибки записан в последней строке каждого журнала `runs/qwen3.7-flash__*/console-log.txt`. До обрыва модель успевала сделать от 0 до 6 вызовов, в одном прогоне дошла до двух графиков.

По правилу протокола дважды сорванный прогон считается невыдержанным, поэтому в `results.md` у Qwen стоит «порядок не держится». Это решение говорит о провайдере в момент прогона. О модели оно ничего не говорит: в колонке «Сорвано сбоем API» у неё 6 из 6.

Вне эксперимента та же модель прошла короткую цепочку из двух вызовов на пробном сервере двумя часами раньше, с исправлением ошибки аргумента. Полную цепочку на Qwen я не проверил.

### Повторная серия после протокола

Через 9 минут после первой серии (15:43 МСК против 15:34) я запустил те же шесть прогонов Qwen ещё раз, отдельной серией: журналы в `runs_qwen_rerun/`, таблица в `results_qwen_rerun.md`. Перед запуском один короткий запрос к модели прошёл. Серия сорвалась так же: 429 во всех шести прогонах и шести повторах, модель успевала сделать от 0 до 4 вызовов.

После этого я отправил по восемь коротких запросов подряд трём моделям Qwen. `qwen/qwen3.7-flash` вернула 429 на первые три и ответила на остальные пять. `qwen/qwen3.8-flash` и `qwen/qwen3.7-plus` ответили на все восемь. Это разовая проверка: она показывает, что лимит относится к одной модели у провайдера и срабатывает непостоянно. Между сериями прошло мало времени, в другой час модель может пройти.

### Серия на `qwen/qwen3.8-flash` после протокола

Чтобы получить результат по семейству Qwen, я прогнал те же шесть прогонов на `qwen/qwen3.8-flash` (0,150 / 0,470 $ за миллион токенов, в списке OpenRouter с поддержкой инструментов). Условия те же: снимок коммита `08f2341`, тот же запрос, те же файлы, тот же скрипт. Журналы лежат в `runs_qwen38_addition/`, таблица в `results_qwen38_addition.md`.

Результат по правилу протокола для одной модели: цепочка выдержана в 6 прогонах из 6, порядок держится; все три закономерности названы в каждом из трёх прогонов на `sales_data.csv`; ошибок инструментов нет. Один прогон сорвался на первом запросе из-за сетевой ошибки (`ConnectError`), повтор по правилу о сбоях прошёл.

Эта модель в протокол не входила, я выбрал её после того, как увидел отказ провайдера по `qwen/qwen3.7-flash`. Поэтому она стоит отдельной строкой и общий вывод о гипотезе не меняет: он посчитан по четырём моделям протокола.

Вывод для клиента: при ответе 429 клиент прекращает анализ и не повторяет запрос. На цепочке из 10–12 запросов одного отказа провайдера хватает, чтобы потерять весь прогон.

## Вторая часть гипотезы

У `mistralai/mistral-nemo` выводов нет вовсе, у DeepSeek и GPT-6.1 названы все три закономерности в каждом прогоне. По правилу протокола вторая часть гипотезы не подтверждена: для неё осмысленные выводы нужны у всех трёх остальных моделей, а Qwen не измерен.

## Где я отступил от протокола

- **Число запусков.** Протокол ограничивал их тридцатью. По протоколу вышел 31: один технический, 18 прогонов трёх моделей и 12 попыток Qwen. Повторы Qwen скрипт сделал сам по правилу о сбоях, каждая попытка оборвалась за 2–24 секунды. Повторная серия Qwen добавила ещё 12 попыток, серия на `qwen/qwen3.8-flash` ещё 7. Всего 50.
- **Две серии после протокола.** Повторную серию `qwen/qwen3.7-flash` и серию на `qwen/qwen3.8-flash` протокол не предусматривал. Обе лежат отдельно и в таблицу `results.md` не входят.
- **Режим в скрипте.** Для повторной серии я добавил в `score.py` ключ `--addition`: он убирает общий вывод о гипотезе. В `results.md` от этого изменилась одна фраза в шапке.
- **Колонка в таблице.** После прогонов я добавил в `score.py` колонку «Сорвано сбоем API». Она показывает число прогонов со статусом `error`. Правила подсчёта и решения я не менял.
- **Расход.** По журналам ушло 0,106 доллара на прогоны по протоколу, 0,002 на технический и 0,029 на серию `qwen/qwen3.8-flash`: всего 0,138. Оборванные попытки Qwen в журнал расхода не попали: клиент пишет стоимость только в конце прогона. Настоящий расход чуть выше.

## Что не проверено

- `qwen/qwen3.7-flash` на полной цепочке. `qwen/qwen3.7-plus` на цепочке не запускал.
- Помогает ли слабой модели подталкивание со стороны клиента («продолжай»). Клиент этого не делает.
- Другие запросы, другие файлы, поздние версии сервера: прогоны шли на коммите `08f2341`.
- Правило поиска закономерностей по ключевым словам я не сверял с ручной разметкой. Три ответа сильных моделей прочитал глазами: закономерности в них названы прямо, с цифрами.

## Как повторить

```bash
python experiments/model_comparison/run_models.py
```

```bash
python experiments/model_comparison/score.py
```

Первая команда пропускает прогоны, для которых уже есть папка в `runs/`. Ключ OpenRouter берётся из `.env`.

Серия после протокола запускается и считается теми же скриптами с другой папкой:

```bash
python experiments/model_comparison/run_models.py --models qwen/qwen3.8-flash --runs-dir experiments/model_comparison/runs_qwen38_addition
```

```bash
python experiments/model_comparison/score.py --runs-dir experiments/model_comparison/runs_qwen38_addition --out experiments/model_comparison/results_qwen38_addition.md --addition
```
